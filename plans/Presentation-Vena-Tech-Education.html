What Is Vena?

A local web dashboard that reads .claude/ project directories and displays:

🤖 Agent Monitoring

Identities, memory files, and activity status for each team agent

💰 Budget Tracking

API budget via the Vault & Valve system with alert levels

🗺️ Roadmap Progress

Phase completion, task checklists, and plan documents

💻 CLI Passthrough

Embedded terminal for direct CLI interaction via xterm.js

Key principle: No database. No cloud. No auth. Reads files directly from disk. Runs entirely on localhost.

Server Components vs Client Components

The most important concept in modern Next.js.

Server Components default

  • Run on the server (Node.js)
  • Can read files (fs.readFileSync)
  • Ship zero JavaScript to the browser
  • Cannot use useState, useEffect, onClick

In Vena: All page.tsx files

Client Components opt-in

  • Run in the browser
  • Can use state, effects, event handlers
  • Must be marked with "use client"
  • Ship JavaScript bundle to browser

In Vena: Sidebar, Terminal, Charts, Errors

Keep components as Server Components unless they absolutely need browser interactivity. This makes the app faster and more secure.

TypeScript: Types as Safety Nets

Without TypeScript

// Bug hides until runtime
function getBalance(ledger) {
  return ledger.remaining_balance;
  // typo? wrong field? No one
  // knows until it crashes
}

With TypeScript

// Bug caught at build time
function getBalance(
  ledger: BudgetLedger
): number {
  return ledger.remainingBalance;
  // TypeScript knows the exact shape
}

Strict Mode Means

No guessing types — any is banned

Null must be checked — if (value !== null) before using

Signatures must match — function calls are validated

The build (npm run build) fails if types don't match. This is intentional — bugs are caught before reaching the browser.

JSONL: The Session Log Format

usage-log.jsonl — one JSON object per line:

{"event":"SessionStart","ts":"2026-03-19T10:00:00Z","session":"s-001","source":"hook"}
{"event":"SessionEnd","ts":"2026-03-19T10:45:00Z","session":"s-001","source":"hook"}
{"event":"SessionSummary","ts":"2026-03-19T10:45:00Z","session":"s-001",
  "phase":"Phase 2","categories":["code_build","tests"],"api_cost_usd":0.42}

Why JSONL Instead of JSON?

Append-Friendly

New events added by appending a line. No need to parse the whole file first.

Stream-Parsable

Each line is a complete JSON object. Can be parsed independently.

Fault-Tolerant

A malformed line doesn't break the whole file. Parser skips bad lines.

The Terminal System

xterm.js + PTY Server — a real terminal in the browser

┌──────────────┐ WebSocket ┌──────────────┐ stdin/stdout ┌──────────┐ │ xterm.js │ ◄──────────────► │ PTY Server │ ◄──────────────► │ Shell │ │ (browser) │ port 3001 │ (Node.js) │ (node-pty) │ (bash/ │ │ │ │ │ │ pwsh) │ └──────────────┘ └──────────────┘ └──────────┘

Data Flow

  1. xterm.js renders terminal UI in browser
  2. Keystrokes sent via WebSocket to PTY server
  3. PTY server writes to real shell (node-pty)
  4. Shell output flows back through WebSocket
  5. xterm.js renders with full color support

Authentication Flow

  1. PTY server generates random token → .pty-auth-token
  2. Browser calls /api/pty-token API route
  3. Browser sends auth as first WebSocket message
  4. PTY server verifies → spawns shell

Security: The 8 Hardening Measures

The PTY server is the most security-sensitive part — it spawns real shell processes.

#ThreatMeasure
S1Network exposureBind to 127.0.0.1 only — never 0.0.0.0
S2Resource exhaustionCap at 5 concurrent sessions
S3Malformed resizeValidate cols/rows as integers 1–500
S4Cross-site hijackCheck WebSocket Origin header
S5Connection floodRate limit: 10 connections/IP/minute
S6Path traversalValidate PTY working directory
S7Memory exhaustionLimit WebSocket messages to 1 MB
S8Unauthorized accessRandom token auth + 5s timeout

Beyond PTY: No database = no SQL injection · No user input = no XSS · No auth = no session hijacking · Local-only = no CORS

React Patterns Used in Vena

Components

Functions that return JSX — the building block of every UI element.

function StatusCard({
  label, value
}) {
  return (
    <div className="...">
      <p>{label}</p>
      <p>{value}</p>
    </div>
  );
}

State & Effects

// State — data that changes
const [open, setOpen] =
  useState(false);

// Effect — runs after render
useEffect(() => {
  setOpen(false);
}, [pathname]);

Refs & Callbacks

// Ref — DOM access
const termRef =
  useRef<XTerm | null>(null);

// Callback — memoized fn
const connect = useCallback(
  async () => { ... },
  [updateStatus]
);

Props = data passed from parent to child (like function arguments). State updates trigger re-renders. Effects run side effects after render. Refs hold mutable values without re-rendering.

Error Handling Strategy

Three layers — never show a blank page or an unhandled crash.

Layer 1: Data Layer (Graceful Nulls)

Every reader returns null or [] if the file doesn't exist. Pages check and show empty states.

const ledger = readBudgetLedger(claudeDir);
if (!ledger) return <EmptyState message="No budget ledger found." />;

Layer 2: Loading States

Every route has a loading.tsx with skeleton placeholders. Next.js shows these automatically via React Suspense while the Server Component fetches data.

Layer 3: Error Boundaries

Every route has an error.tsx — a Client Component that catches runtime crashes and shows a recovery UI with a "Try again" button.
